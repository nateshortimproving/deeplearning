# PRD Output file being judged: /Users/nateshort/Desktop/ImprovingDeepLearning/PRD-csv-report-export.md

## Missing Requirements

- **CSV injection (formula injection) escaping.** No requirement addresses fields beginning with `=`, `+`, `-`, `@`, or tab/CR characters that Excel, Sheets, and LibreOffice execute as formulas/DDE on open. The PRD's stated goal — "opens cleanly in Excel" — combined with exporting potentially attacker-controlled field values (names, notes, titles) makes this a security requirement, not a nicety. Given the document already takes security seriously (permissions, audit logging, GDPR constraints), the most common real-world CSV-export vulnerability is conspicuously absent.
- **Pagination semantics.** "Exactly the rows… currently applied to the report on screen" never defines whether the export contains all rows matching the filters across all pages, or only the currently rendered page. Every report UI paginates; users will interpret "what's on screen" differently. This single ambiguity will generate more bug reports than any other part of the spec and needs an explicit P0 decision.
- **Sort order.** "As filtered and configured on screen" implies it, but no requirement states the CSV preserves the report's current sort order — including multi-column sorts and whether a client-side-only sort is re-applied server-side.
- **Aggregated/report-structure columns.** Reports with totals rows, subtotals, grouped/banded headers, pivot/crosstab layouts, or drill-down hierarchies cannot be represented by "header row + flat rows." The PRD assumes every report is a flat table. How a two-row grouped header flattens to one CSV header line, whether totals/subtotals export, and how indentation/grouping is represented are all unspecified.
- **Sort/filter state snapshot for audit fidelity.** The audit log captures "user, report, row count, timestamp" but not the filter values, date range, or column set. For the named compliance audience, this log cannot reconstruct or prove *what* was exported — only that something was. The compliance user story ("audit record faithful to what was reviewed") is unsupportable with the specified log fields.
- **Partial-failure behavior.** No requirement defines behavior when generation fails mid-stream or the connection drops mid-download: is the partial file discarded, does the UI offer retry, can the user receive a truncated CSV that *looks* valid? The metric demands no "truncated output," yet no requirement makes truncation detectable (e.g., server-side completion before response, a trailer row, or Content-Length integrity).
- **Column-level masking parity.** "Only data the requesting user is authorized to view" is report-level. If the UI masks field values (SSN last-4, salary bands, PII obfuscation) while the underlying query returns raw data, a re-run server-side export can leak the unmasked values. Field-level security parity must be an explicit requirement.
- **Export permission as a distinct control.** The PRD ties export rights to view rights and assumes the permission model "can be applied to exports." Many organizations deliberately separate "view" from "export" (exfiltration control) — e.g., view a report but cannot download it. This policy decision is silently made by an assumption rather than surfaced as a requirement or open question.
- **Timezone and locale specification.** "Dates formatted consistently with the UI" never states whose timezone — viewer's locale, report-configured zone, or UTC. Exporting "now"-sensitive timestamps in the viewer's tz vs. the auditor's tz changes the data. Similarly, the filename's `export date` uses an unstated timezone, and decimal separators/locale (comma-vs-semicolon-delimited Excel in European locales) directly undermine "opens cleanly in Excel."
- **Rate limiting / concurrency caps.** Constraints require exports to be "bounded in memory/time" per-export, but nothing bounds a single user hammering export on a 99k-row report, or N users exporting simultaneously. A bounded per-request cost times unbounded concurrency is unbounded load.
- **Instrumentation for the adoption metric.** "≥30% of active report viewers use CSV export" and "decline in support feature requests" require emitting analytics events (exposed/clicked/completed per user per report) and a mechanism for categorizing support tickets. No functional requirement mandates this telemetry; the metrics presuppose infrastructure never specified.
- **UI placement and states.** No requirement covers where the action lives (toolbar, overflow menu), its label/icon, keyboard/screen-reader accessibility, loading/disabled state during generation, or error presentation. "An Export to CSV action on every report view" leaves the entire interaction undefined.
- **Download mechanism.** Dependencies note "frontend capability to trigger a file download (or streamed response)" but no requirement picks a mechanism — Content-Disposition streaming vs. generate-then-serve vs. blob — which drives whether progress, retry, and timeout behavior are even possible.
- **NULL/empty and special-value serialization.** How NULLs, empty strings, very long text, embedded HTML/markup, hyperlink cells, image/chart columns (sparklines, thumbnails), and multi-value cells serialize is unspecified. A report cell that is a link or an image has no defined CSV representation.
- **Non-latin/unicode filename handling and illegal characters.** Report names containing `/`, `:`, `\`, quotes, or emoji must be sanitized into a legal cross-platform filename; unspecified.
- **Rollout and versioning.** No phased rollout/flag requirement despite touching "every report view," and no schema-stability policy: headers are bound to UI labels, so a UI column rename silently breaks downstream pipelines keyed on headers — with no versioning or deprecation stance.

## Logical Errors

- **"Exactly what was on screen" vs. re-running the query.** The core P0 promise — export equals on-screen state — conflicts with the stated mechanism — "the same query can be re-run server-side for export." For any mutable dataset, the re-run query at export time returns *different* rows than the snapshot rendered earlier. The compliance user story demands a faithful record of "what was reviewed," which re-querying cannot guarantee. The constraint forbids a *different query path* but ignores *different query time*; snapshot-vs-requery is the fundamental design fork and the PRD never reconciles it.
- **"Rejected before generation" presupposes a cheap count.** The P1 requirement to reject oversized exports before generation requires knowing the row count without generating — i.e., a separate COUNT query or estimate. For complex reports, the count can cost as much as the export itself. The user story ("told upfront") makes a UX promise whose feasibility is unverified and whose cost is unacknowledged in Dependencies.
- **Mandatory constraint vs. P1 requirement on audit logging.** Constraints state logging and permission checks are "mandatory," while the functional requirement assigns audit logging P1. A mandatory constraint cannot be satisfied by a priority-1 (presumably deferrable) requirement — either logging is P0 or the constraint is aspirational.
- **Success metric penalizes designed behavior.** "≥99% of *initiated* exports complete successfully" — a correctly rejected >100k-row export is an initiated export that does not complete. The metric as written counts the guard working as intended against the success rate; the denominator must exclude (or separately track) expected rejections.
- **"Disabled or hidden only when the user lacks permission to view that report" is vacuous.** A user who can't view the report never sees the report view, so the condition can never arise. The requirement was clearly meant to address export-vs-view permission separation but instead specifies a state that cannot exist.
- **Display-format consistency vs. data fidelity.** P2 formats values "consistently with the report UI's display formats," but display formatting destroys data: UI shows "$1.2K" or rounds to two decimals, and exporting the display string exports the rounding — a corrupted value in a "data fidelity" feature. The fidelity goal of the export and the display-fidelity requirement are in direct tension; the raw-vs-formatted question parked in Open Questions is actually a decision that changes what P0 ("exactly the rows") means.
- **"Standards-compliant" vs. BOM and Excel-centric formatting.** The PRD claims RFC 4180 compliance while mandating a UTF-8 BOM (not part of RFC 4180 and a known parser-breaker in non-Excel pipelines) and Excel-targeted formatting of leading zeros. The file cannot simultaneously be optimized for Excel and strictly standard/clean for "data pipelines" — a real tension the PRD papers over.
- **Metric unverifiable by its own method.** "Exported rows match on-screen report rows 1:1 in QA sampling" — QA sampling cannot validate production behavior, and on mutable data the screen and export can legitimately differ, making the 1:1 comparison undefined without a snapshot definition.
- **Binary export model ignores the middle zone.** Exports are either "inline" or "rejected." Between a typical report and the 100k limit lies a large band (e.g., 50k rows) where synchronous generation exceeds HTTP/browser timeouts. The PRD specifies no timeout bound, so a class of *allowed* exports will fail by timeout with no designed UX — and the async fallback for exactly this band is deferred to v2.
- **"Every report view" vs. unverified uniformity.** P0 requires the action on every report view, but Assumptions concede the same query must be re-runnable server-side — which cannot hold for reports with client-side joins, post-processing, or widget-composed data. The universal P0 rests on an assumption that is almost certainly false for at least one report type, and the PRD has no exclusion mechanism.

## Edge Cases

- **Formula-injection payload in data.** A cell value `=cmd|'/c calc'!A1` or `=HYPERLINK("http://evil","click")` in a name/note field exports verbatim and executes when the recipient opens the file — turning the export feature into a phishing delivery mechanism.
- **Data mutated between view and export.** Rows updated/deleted between report render and export click produce a CSV that contradicts the audit story; conversely, a report left open overnight exports "stale" filters against new data with no warning.
- **Double-click / retry storms.** Impatient users clicking export repeatedly on a large report multiply server load; no idempotency, debounce, or concurrent-export-per-user limit is specified.
- **Duplicate filenames.** Two same-day exports of the same report produce identical filenames (`report-2026-10-19.csv`), silently overwriting or confusing audit trails; no disambiguator (time, sequence) is specified.
- **Illegal/special characters in report names → filenames.** `Q3/Q4 Rev: Summary` cannot be a filename; sanitization, length limits, and unicode normalization are unspecified.
- **Embedded newlines corrupt row counting.** RFC 4180 permits newlines inside quoted fields; a line-count then overstates row count vs. the logged "row count," and naive downstream tools miscount — the audit log's `row_count` needs a definition (records vs. lines).
- **Duplicate or empty column headers.** Two UI columns both labeled "Name," or an unnamed computed column, yield ambiguous/blank headers that break keyed pipeline ingestion.
- **Excel cell and row limits.** Cells exceeding Excel's 32,767-char limit are silently truncated on open; if the row limit ever rises past 1,048,576 the file won't fully open in the product's own reference tool. No maximum-cell-content policy exists.
- **NULL vs. empty string vs. "N/A".** Undefined serialization means empty fields may round-trip as the literal text "null" or lose the NULL/empty distinction — a data-fidelity bug that QA 1:1 sampling may not catch.
- **Timezone boundary exports.** A date-range filter "through Oct 19" exported near midnight in a different zone than the report was configured for yields a different row set; filename date and filter resolution can disagree.
- **Locale-delimited Excel.** Users in locales where Excel expects `;` delimiters (and `,` is the decimal mark) get single-column garbage from a compliant comma CSV — "opens cleanly in Excel" fails by geography.
- **Sort/locale instability.** Client-side case-insensitive sort vs. server collation produces a differently-ordered CSV than the screen shows; "exactly as configured" fails subtly.
- **Export while a shared report's definition changes.** A teammate edits the saved report's columns between view and export; which configuration does the export honor — the user's rendered snapshot or the current saved definition?
- **Navigation away / tab close mid-download.** Behavior on cancel, and whether a cancelled download logs as a completed export event, is unspecified — corrupting both UX and the audit metric.
- **Masked-but-exportable fields.** UI shows `***-**-1234`; the re-run query returns the full value. The single most damaging export bug possible and it falls out of the architecture unless explicitly handled.
- **Report view with zero columns or transient error state.** A view rendered in an error/empty state that still shows the export button exports a meaningless or stale file.

## Quality Gaps

- **Undefined priority legend.** P0/P1/P2 are used without definition; readers cannot tell whether the row-limit guard and audit logging (P1) are launch-blocking. Combined with the "mandatory" constraint language, the priority semantics are internally inconsistent.
- **No acceptance criteria.** Requirements are directional ("opens cleanly," "bounded in memory/time," "complete inline for typical sizes") with no pass/fail tests, no defined thresholds for "typical," "bounded," or "complete inline."
- **Example-grade parameter in a requirement.** "(e.g., 100k rows)" places an undecided value inside a P1 shall-statement; the limit is simultaneously a requirement and an open question.
- **Metrics without measurement plans.** All five success metrics lack instrumentation requirements, denominators (what counts as "initiated" vs. "rejected"), baselines (support-request decline), or owners. "Zero permission-escalation incidents" is unauditable without the export-content forensics the current log fields can't provide.
- **Foundational assumption unverified.** The entire architecture depends on "the same query can be re-run server-side," asserted as an assumption rather than validated by a technical spike. If false — which is likely for some report types — the P0 feature and the constraint forbidding a divergent query path cannot coexist.
- **Open questions that are actually requirements.** The metadata-header question changes the file contract for every pipeline consumer; the raw-vs-formatted question changes what "exactly as on screen" means; the async-fallback question determines whether a large class of legitimate exports simply fails in v1. Deferring these defers load-bearing decisions, not refinements.
- **Audit log underspecified for its stated purpose.** Field list (user, report, row count, timestamp) lacks filters/date range/columns, so the log cannot demonstrate what data left the system — the core of the compliance use case. Retention, access control, and tamper-evidence of the log itself are unstated.
- **No abuse/misuse analysis.** CSV export is a bulk-exfiltration vector; there is no mention of rate limits, anomaly detection, admin alerting on large/unusual exports, or DLP interaction — notable given the document itself raises GDPR obligations for downloaded files.
- **Missing non-functional bounds.** No timeout ceiling, concurrency limit, memory cap value, or maximum file size. "Bounded in memory/time" is unverifiable without numbers; the 5-second metric covers only ≤10k-row reports, leaving the 10k–100k band unbounded.
- **No error-handling spec beyond the row limit.** Failures other than oversize (query timeout, permission revoked mid-request, serialization error) have no specified UX, retry semantics, or supportability (error IDs, user-facing vs. logged detail).
- **Localization unaddressed.** UI-localized headers make CSV schemas unstable across locales (a French user's header row differs from a US user's), breaking the "data pipelines" audience the PRD names — with no decision on whether headers follow UI locale or a stable key.
- **No scope statement on platform surface.** "Every report view" doesn't state whether this includes mobile web, embedded/iframe reports, or shared/public report links — each a different permission and download-mechanism problem.
- **Ambiguous filename contract.** "Identify the report and export date" with one example leaves slug rules, timezone, uniqueness, and character sanitization undefined — trivially testable details left to implementer discretion across every report.
