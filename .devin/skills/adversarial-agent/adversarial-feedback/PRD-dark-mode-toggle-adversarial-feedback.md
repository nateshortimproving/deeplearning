# PRD Output file being judged: /Users/nateshort/Desktop/ImprovingDeepLearning/PRD-dark-mode-toggle.md

## Missing Requirements

- **Analytics/telemetry instrumentation.** Two success metrics (≥25% adoption, ≥95% persistence integrity) are impossible to measure without logging theme selection and persistence outcomes, yet no functional requirement mandates emitting these events. The metrics presuppose infrastructure the PRD never requires anyone to build.
- **Cold-start theme application.** The PRD requires no-flash switching for *transitions* (P1) but is silent on the launch path: reading the persisted preference, resolving "System" against the OS trait, and applying the palette *before the first frame renders*. The most common real-world defect in this feature — a white flash on cold launch for dark-mode users — is unaddressed. This also undermines the user story "never surprised by a bright screen on launch."
- **Splash screen / app icon / launch screen.** The iOS launch screen storyboard and Android launch window render before app code runs and are outside the theme layer. They are not listed in scope or as an edge case, and no asset requirement covers them.
- **Migration behavior for existing installs.** The single most consequential product decision — whether existing users silently flip to "System" (potentially changing their UI overnight) or stay "Light" — is parked in Open Questions with a self-contradictory "recommendation." It should be a decided P0 requirement, not an open question, because it changes what the app does on day one for the entire install base.
- **Invalid/corrupted preference handling.** No requirement specifies behavior when the persisted value is unreadable, out of range, or written by a different app version (e.g., a downgrade that doesn't understand the "system" enum value). Standard practice: fall back to "System" or "Light" and self-heal the stored value.
- **Accessibility beyond contrast.** WCAG AA contrast is covered, but nothing addresses: Reduced Motion for the theme transition, VoiceOver/TalkBack labeling and ordering of the new control, Dynamic Type/text scaling inside the dark palette, or iOS "Increase Contrast"/"Reduce Transparency" modes. Given "accessibility-sensitive users" are a named target audience, this is a material gap.
- **Non-text surfaces.** Charts, graphs, maps, syntax-highlighted code, badges, empty-state illustrations, and images with baked-in light backgrounds are unaddressed. "Dark variants of branded imagery" (P2) covers marketing assets only, not data visualization, which is where dark-mode implementations most often break.
- **First-party web views.** Out of scope correctly declines to force-dark *third-party* web content, but the PRD never addresses first-party web views (help pages, terms, auth flows in a webview) — a common source of a jarring white screen inside a dark app.
- **Cross-device/account sync.** "Persists locally" implies device-local only, but the PRD never states whether a signed-in user's preference should sync. If the app has accounts, users on multiple devices will file this as a bug.
- **Discoverability.** The adoption metric (≥25% in 60 days) has no supporting requirement for how users learn the setting exists — no onboarding prompt, no settings-badge, nothing. Metrics without a mechanism are wishes.
- **Localization.** New settings strings ("Theme", "Light", "Dark", "System") need localization; unmentioned.
- **OEM/forced-dark interference.** Android OEM "force dark" features (MIUI, ColorOS, developer option) can double-apply darkening on top of the app's own palette. No requirement to detect or disable forced darkening (`android:forceDarkAllowed="false"`) on properly themed screens.

## Logical Errors

- **P0 requirement vs. 95% metric contradiction.** "The system *shall* persist the user's theme selection" is a P0 absolute, while the metric accepts a 5% failure rate ("≥95% persist correctly"). Either persistence is a hard requirement (metric should be ~100%, with failures treated as bugs) or it's best-effort (it shouldn't be P0 "shall"). As written, the PRD permits a measurable failure of its own mandatory requirement.
- **100% contrast audit vs. unthemeable surfaces.** The metric requires WCAG AA on "100% of screens," while Constraints acknowledge third-party SDK surfaces "we cannot theme" that "must not break visually." A mixed-appearance screen is precisely where contrast fails; these two statements cannot both hold without an explicit carve-out defining which surfaces the audit excludes.
- **"Recommended" open question that doesn't recommend.** Open Question 1 says "Recommended: 'System' for new installs, 'Light' migration for existing installs is defensible either way" — that is two different options restated, not a recommendation. And "new installs default to System" is already a decided P1 requirement, so the question only needs to cover existing installs.
- **Metric that conflates action and state.** "≥25% of active users enable Dark or System-with-dark" mixes an explicit user action (choosing Dark) with a passive state (System default + dark OS). Users who never touched the setting count toward "enable." The metric can't distinguish feature adoption from OS-usage distribution and gives no way to detect a broken selector if the number looks fine.
- **Unmeasurable metric phrasing.** "No dropped frames perceptible in UI testing" and "must not break visually" are subjective; "≥95% persistence" is measurable only "via preference-integrity logging *or* QA regression" — QA regression cannot produce a field-percentage. The metric's own measurement method is incapable of generating the metric.
- **Constraint smuggling a design decision.** "Pure-black vs. pure-white choices must be deliberate" is not a constraint — it's a note to the design team. It is also untestable as written ("deliberate" has no pass/fail).
- **Scope inconsistency on surfaces.** Out of scope excludes "surfaces outside the app shell" (widgets, notifications, icon), but Dependencies require status-bar styling — which is also outside the app shell. The boundary line is drawn inconsistently; either system chrome is in scope or it isn't.
- **Bounded-effort claim contradicts scope breadth.** "Effort is bounded by auditing every existing screen — broad but shallow" assumes a complete token refactor exists ("will be refactored to be"). If the token layer doesn't already exist, this is a deep change — every hard-coded color in every view — and the PRD's effort framing is wrong.

## Edge Cases

- **Flash-of-unthemed-content at cold start.** Persisted preference read races first-frame render; if the theme resolves late, dark users see a white flash — the single most common complaint about dark-mode launches and exactly what the light-sensitive user story promises won't happen.
- **OS appearance change mid-transition.** The OS switches at sunset while the user is in a modal, a navigation push, a payment sheet, or mid-form. Live-following the OS during a transaction can re-render and drop form state, scroll position, or an in-flight payment UI.
- **Backgrounded app waking to a different OS theme.** Covered by "update live," but the re-render on foreground must handle views that were snapshotted for app-switcher previews — the system task-switcher thumbnail may show the *old* theme.
- **Downgrade/upgrade preference corruption.** App v1.1 writes `theme=system`; user downgrades to v1.0 which expects `light|dark`. Reads garbage → crash or wrong theme. Needs a tolerant parse + default.
- **Rapid toggling.** User flips Light↔Dark repeatedly; transition animations must queue/cancel cleanly without leaving a half-tokenized UI (some views dark, some light).
- **Smart Invert / accessibility inversion.** iOS Smart Invert inverts app colors; combined with dark mode it double-inverts to a broken light-ish UI. Needs explicit handling or documented non-support.
- **OEM force-dark double-darkening.** Manufacturer darkening applied over the real dark palette produces illegible muddy colors on some Android devices.
- **Multi-window contexts.** Split-screen, Stage Manager, foldables, and in-app picture-in-picture surfaces can host screens not enumerated in "every existing screen" audits.
- **Theme change during in-flight async content.** A screen mid-load (images fetched with light-variant URLs, themed remote config) when the theme flips can finish rendering in the stale palette.
- **System option on an OS without an appearance API.** Assumptions cover iOS 13+/Android 10+, but if any supported OS version lacks the API (or an OEM reports it unreliably), "System" needs a defined fallback — unspecified.
- **Settings screen self-rendering.** The screen hosting the toggle must re-theme itself mid-interaction, including the control's own selected-state styling, without a flicker loop.

## Quality Gaps

- **Undefined priority legend.** P0/P1/P2 are used but never defined. Readers can't tell if P1 means "required for launch" or "nice to have" — this directly affects whether the no-flash transition and System-default ship.
- **No testable acceptance criteria.** Requirements are directional ("does not flash," "must not break visually") with no pass/fail definition. Each P0 needs at least one verifiable criterion.
- **No screen inventory or audit deliverable.** "Every existing screen" is asserted as bounded scope but no artifact (checklist, screenshot matrix, screen count) is required to prove coverage. There is no way to know when the work is done.
- **Missing non-functional requirements.** App-size impact of dual assets, memory cost of two palettes, startup-time regression from preference resolution — none bounded.
- **Metrics lack owners, instrumentation, and rollout linkage.** No measurement plan, no named instrumentation work, and the rollout question (flag vs. 100%) is unresolved while metrics assume a population to measure. Staged rollout changes the denominators.
- **Dependencies without owners or fallback.** "Complete, approved dark design-token palette" is a hard blocker with no owner, deadline, or contingency if design slips — yet it's the gating dependency for everything else.
- **Assumptions doing requirement work.** "Minimum supported OS versions expose a system appearance API" is load-bearing: if false, "System" is undeliverable and a P0 requirement silently breaks. This should be verified and promoted to a constraint with a fallback, not left as an assumption.
- **No failure-state or error-boundary spec.** What the app does when persistence write fails (disk full, permissions) is undefined — does it silently revert the toggle? Show nothing? At minimum, behavior should be specified.
- **Audience/platform ambiguity.** Everything reads mobile-only (iOS/Android APIs), but the doc never states the platform set. If the app also ships desktop/web, the entire spec silently excludes it.
- **No definition of done for third-party surfaces.** "Must be audited" and "must not break visually" with no inventory of SDK surfaces, no owner, and no acceptance bar. This is a known risk area left as a shrug.
